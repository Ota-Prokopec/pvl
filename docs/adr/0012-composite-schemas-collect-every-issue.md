# Composite schemas collect every field's `Issue` rather than failing fast

`pvl.object()` validates every declared field even after an earlier one has failed, returning one `Result` whose `issues` array holds an `Issue` per failing field (plus one per unrecognized key under `.strict()`), rather than returning as soon as the first field fails. The same rule is meant to hold for the other composites as they land — `array` reports every failing element, `union` reports what every member rejected.

The driver is the shape of the thing being validated. A composite's typical caller is checking a whole payload — an HTTP body, a form submission, a third-party API response — against a shape, and wants to tell the user everything wrong with it in one pass. Fail-fast turns that into as many validate-fix-resubmit round trips as there are bad fields, and the information needed to avoid them was already computed and then thrown away. `Issue.path` exists precisely so several issues from one `Result` can each be attributed to their own field, which only pays off if more than one can be reported at a time. It is also what `StandardSchemaV1` expects: its failure branch is an `issues` array, not a single issue.

Primitives still return a single `Issue` and stop at their first failing check — a `pvl.string().min(3).max(5)` that isn't a string has nothing further to meaningfully check, and its constraints are ordered checks on one value rather than independent sub-validations. So "collect everything" is a composite-level rule about independent children, not a package-wide one about every check.

The cost is that a failing composite does strictly more work than it needs to in order to answer "is this valid?" — every field is validated even once the answer is known to be no. That is accepted: the library's performance target is the success path (the common case, where every field must be visited anyway), and `@pvl/schema-compiler`'s eventual compiled output is free to make the same trade, since it compiles the same semantics.
