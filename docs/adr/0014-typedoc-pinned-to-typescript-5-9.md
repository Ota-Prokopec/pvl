# TypeDoc runs against TypeScript 5.9 in `apps/docs`, not the repo-wide 7.0.2

The documentation site at [`apps/docs`](../../apps/docs/AGENTS.md) generates its API reference with TypeDoc, which reads `@pvl/schema`'s source and therefore needs a TypeScript compiler it accepts. TypeDoc `0.28.20` declares `peerDependencies.typescript: "5.0.x || … || 5.9.x || 6.0.x"`, and TypeScript 6.0.0 stable was never published — npm carries only `6.0.0-beta` — so the newest stable TypeScript TypeDoc accepts is `5.9.x`. This repo pins `typescript: 7.0.2` everywhere else, which TypeDoc will not run against at all.

`apps/docs` therefore declares its own `typescript: ~5.9.3` devDependency. pnpm isolates it to that workspace entry, so `@pvl/schema` and every other package keep building and type-checking on 7.0.2, and only the documentation generator ever sees 5.9. The two compilers never meet: TypeDoc parses the schema source with 5.9 to extract TSDoc, and nothing it produces feeds back into a build.

This is safe today because nothing the doc generator has to parse is TypeScript-7-only. `packages/typescript-config/base.json` uses `NodeNext`, `isolatedModules`, `noUncheckedIndexedAccess` and `ES2022`, all of which 5.9 understands, and the most modern syntax in `packages/schema/src` is `const` type parameters, which landed in TypeScript 5.0. The standing risk is that TypeScript-7-only syntax added to the schema source later breaks documentation generation with an error that points at the syntax rather than at this pin — hence this record.

Three alternatives were rejected. Forcing TypeDoc onto 7.0.2 via `pnpm.overrides` fails at runtime rather than at install time: TypeDoc reaches into TypeScript's internals, and 7.0 is the native rewrite, so satisfying the version range says nothing about whether the internals it calls still exist. Pointing TypeDoc at `packages/schema/dist/*.d.ts` instead of source does not help, because it still needs a compiler it accepts to read those declarations — and declaration output strips context that `excludeInternal` filtering depends on, which is the reason the [entry point is source](../../apps/docs/AGENTS.md) in the first place. Waiting for TypeDoc 1.0, which exists only as `1.0.0-dev.4`, would mean shipping the site with no API reference at all.

**Revisit when TypeDoc 1.0 ships with TypeScript 7 support.** At that point `apps/docs` drops its local `typescript` devDependency and rejoins the repo-wide pin.
