# Composites accept any Standard Schema as a field, re-prefixing the child's Issue paths

`ObjectSchema` and `ArraySchema` accept any `StandardSchemaV1` as a field or element, not only a `@pvl/schema` `Schema`. When a field is not one of this package's own classes, the composite calls the child's `~standard.validate` and, for every `Issue` that comes back, prepends its own key (or array index) to the child's `path` before collecting it.

This exists first of all because a nested [Compiled Schema](../../CONTEXT.md) is such a field. A Compiled Schema is a Standard Schema object and nothing more — it has no `_validate` and no place in `@pvl/schema`'s class hierarchy — so without this an interpreted parent could not hold a compiled child, and partial adoption of the compiler would not compose at all. Path re-prefixing is what makes that child satisfy [ADR-0012](./0012-composite-schemas-collect-every-issue.md)'s contract: the parent reports every failing field, each attributed to its own location, and a failure two levels inside a compiled child still names its full path from the outermost Schema, so a consumer's error rendering keeps pointing at the right field after the import swap.

Accepting _any_ Standard Schema rather than special-casing Compiled Schemas is the same work for a strictly better result. Standard Schema was adopted ([ADR-0001](./0001-adopt-standard-schema.md)) precisely so the boundary is a protocol rather than a class, and honouring it on the consuming side too means a Zod or Valibot schema drops into a `pvl.object` unchanged — useful at exactly the boundaries where schema libraries meet.

Two consequences are worth stating. The child owns its own `Issue` shape, so a foreign schema's issues arrive carrying whatever `message` that library produces and, unlike `@pvl/schema`'s own, need not carry an `Issue.code`; the parent re-prefixes the path and otherwise passes them through rather than normalising them. And Standard Schema's `validate` may return a `Promise`, which `@pvl/schema`'s existing synchronous-only rule already answers: there is no async validation in v1, so a field whose `validate` returns one cannot be honoured. How that surfaces follows the package's standing rule that thrown errors are for programmer error and `Issue`s are for invalid values.
