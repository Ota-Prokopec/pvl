# No regex-backed constraint helpers in v1

`@pvl/schema`'s built-in constraint methods are limited to cheap structural checks — `.min()`, `.max()`, `.length()`, `.int()` — plain numeric/length comparisons only. Regex-backed helpers common in other schema libraries (`.email()`, `.url()`, `.regex()`) are deliberately not built into any v1 schema type; a consumer who needs one attaches it as their own `.refine()`. This keeps every built-in primitive/composite check on the fast, non-regex hot path that both is the runtime path for every schema built on top of it and the performance baseline `@pvl/schema-compiler`'s compiled output is trying to beat — regex execution cost is real and shouldn't be paid by every schema whether or not it uses a format check. The trade-off: a consumer wanting email/URL validation writes their own `.refine()` rather than reaching for a one-line built-in; this is deferred, not ruled out permanently — a future version could add these as an explicit opt-in module rather than the default primitive surface.
