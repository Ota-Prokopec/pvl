# Chained-instance-method API via a shared base `Schema` class

Every `@pvl/schema` modifier (`.optional()`, `.nullable()`, `.refine()`, `.transform()`, `.coerce()`, and `object`'s `.strict()`/`.passthrough()`) is a method on the schema instance that returns a schema, not a wrapping function or static combinator (`pvl.string().optional()`, never `pvl.optional(pvl.string())`). This matches the Zod-style ergonomics the library is modeled on and lets modifiers compose left-to-right in application order. To implement the common modifiers and Standard Schema conformance exactly once rather than duplicating them across every primitive/composite class, all concrete schema classes (`StringSchema`, `ObjectSchema`, etc.) extend one abstract base `Schema` class that owns `"~standard"` and the common modifier methods; a concrete subclass adds only what's specific to its own shape. The trade-off is a single class hierarchy every schema type must fit into, rather than, say, standalone functions per modifier — judged worth it for the consistency and the one-implementation guarantee for Standard Schema conformance.

## Amendment: modifiers preserve the concrete schema class

The base class's modifiers originally declared their return as `Schema<Input, Output>`, which threw away the concrete subclass: a refined `ObjectSchema` was no longer statically an `ObjectSchema`, so `pvl.compile()` — which only accepts a composite — rejected it, blocking the very case `@pvl/schema-compiler` promises to support (a Compiled Schema carrying a Refinement). The modifiers now preserve the concrete class:

- `.refine()` returns `this`. A Refinement changes neither `Input` nor `Output`, so there is nothing to widen, and every schema type keeps its own methods chainable afterwards.
- `ObjectSchema` and `ArraySchema` carry `Input` and `Output` as trailing type parameters (defaulted to the types they derive from their shape/item), and override `.optional()`, `.nullable()` and `.transform()` to return themselves with those parameters widened. The overrides re-state a type only — the runtime value is still the base class's prototype-preserving clone. `ObjectSchema`'s `.strict()`/`.passthrough()` carry those parameters through rather than re-deriving them from the shape, so chaining order is free in both directions; re-deriving would have let `.optional().strict()` claim statically that a schema which still accepts `undefined` at runtime does not.
- On a primitive, `.optional()`, `.nullable()`, `.coerce()` and `.transform()` still widen to the base `Schema`. A primitive is never a `pvl.compile()` candidate, so nothing is earned by giving every primitive class the same two parameters, and the base return type is what keeps `.min()`-style constraints off a schema whose accepted types have moved on.

`CompileCandidate` is stated as `ObjectSchema<ObjectShape, unknown, unknown> | ArraySchema<ArrayItem, unknown, unknown>` so a widened composite still matches it.

One consequence had to be settled in the same change. A constraint method (`.min()`/`.max()`/`.length()`/`.int()`) used to rebuild its schema from its constraints alone, dropping any modifier applied earlier — a defect that the old return types made unreachable except through a cast, and that class-preserving modifiers would have made reachable and silent. Those methods now clone through the base class's `_withModifiers()` and re-point the check list on the clone, exactly as `ObjectSchema`'s `.strict()`/`.passthrough()` already did, so the Shared Modifiers survive a constraint chained after them and chaining order no longer changes what a schema validates.

## Amendment: Shared Modifiers and decision logic factored into `sharedModifiers.ts`

The record of Shared Modifiers (`SharedModifiers`, its step types) and the decision logic that consumes it during `_validate` (the optional/nullable short-circuit, and the ordered refine/transform step runner) were later factored out of the base `Schema` class's own module into a dedicated, colocated `schemas/sharedModifiers.ts`, so that logic is unit-testable as plain functions without constructing a full schema instance. The record is deeply `readonly` and is never mutated: `_withModifiers()` `Object.create`s a prototype-preserving clone carrying a fresh record, which is why the modifiers that hold only for one Schema class — the Local Modifiers, such as `string`'s constraints or `object`'s unknown-key mode — stay on those classes rather than joining this record. This is **not** a reversal of this ADR's decision: `Schema` remains the single class hierarchy every concrete schema extends, and still owns `"~standard"`, `_validate`, and every Shared Modifier method's public surface — `_validate` merely delegates the short-circuit decision and step-running to `sharedModifiers.ts`'s functions instead of containing that logic inline. `sharedModifiers.ts` is deliberately excluded from `@pvl/schema`'s barrel — its exports are an internal implementation detail, not part of the public API.
