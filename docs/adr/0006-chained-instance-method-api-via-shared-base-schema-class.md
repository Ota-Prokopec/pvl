# Chained-instance-method API via a shared base `Schema` class

Every `@pvl/schema` modifier (`.optional()`, `.nullable()`, `.refine()`, `.transform()`, `.coerce()`, and `object`'s `.strict()`/`.passthrough()`) is a method on the schema instance that returns a schema, not a wrapping function or static combinator (`pvl.string().optional()`, never `pvl.optional(pvl.string())`). This matches the Zod-style ergonomics the library is modeled on and lets modifiers compose left-to-right in application order. To implement the common modifiers and Standard Schema conformance exactly once rather than duplicating them across every primitive/composite class, all concrete schema classes (`StringSchema`, `ObjectSchema`, etc.) extend one abstract base `Schema` class that owns `"~standard"` and the common modifier methods; a concrete subclass adds only what's specific to its own shape. The trade-off is a single class hierarchy every schema type must fit into, rather than, say, standalone functions per modifier — judged worth it for the consistency and the one-implementation guarantee for Standard Schema conformance.
