# Composites accept any Standard Schema `@pvl/schema` produced as a field, re-prefixing the child's Issue paths

`ObjectSchema`, `ArraySchema` and `UnionSchema` accept as a field, element or member any Standard Schema that this library produced: an interpreted `Schema` built by a `pvl.*` factory, or a [Compiled Schema](../../CONTEXT.md) produced by `@pvl/schema-compiler`. That set is exactly the Standard Schemas whose `~standard.vendor` is `'@pvl/schema'` — every `pvl` Schema reports that vendor, and per [ADR-0003](./0003-compiled-schemas-conform-to-standard-schema.md) so does every Compiled Schema. `@pvl/schema` therefore types `vendor` as that literal rather than `string`, and the composites' field type (`PvlStandardSchema`) requires it. When a child is not one of this package's own classes, the composite calls its `~standard.validate` and, for every `Issue` that comes back, prepends its own key (or array index) to the child's `path` before collecting it.

This exists because a nested Compiled Schema is such a field. A Compiled Schema is a Standard Schema object and nothing more — it has no `_validate` and no place in `@pvl/schema`'s class hierarchy — so without this an interpreted parent could not hold a compiled child, and partial adoption of the compiler would not compose at all. Path re-prefixing is what makes that child satisfy [ADR-0012](./0012-composite-schemas-collect-every-issue.md)'s contract: the parent reports every failing field, each attributed to its own location, and a failure two levels inside a compiled child still names its full path from the outermost Schema, so a consumer's error rendering keeps pointing at the right field after the import swap.

**Schemas from other Standard Schema libraries are deliberately not accepted.** This record originally accepted any `StandardSchemaV1`, on the grounds that it was the same work as special-casing Compiled Schemas; it was narrowed before anything was built on it. Restricting the boundary to this library's own vendor keeps two guarantees every `pvl` Result carries today and that a foreign child would break: every `Issue` has an `Issue.code` ([ADR-0011](./0011-result-failure-branch-carries-pvl-issue.md)), and `validate` is synchronous — a foreign `validate` may return a `Promise`, which `@pvl/schema`'s synchronous-only rule has no way to honour. Narrowing the vendor and `validate`'s return type at the type level makes both guarantees structural, so the composite passes a child's Issues through without normalising them.

The restriction is enforced at the type level only. The factories do not inspect a child's vendor at runtime: the check would cost every construction something to catch only a caller who has already cast past the type, and a thrown error there is reserved for programmer error anyway. The accepted cost is that a mixed-library boundary — a Zod schema inside a `pvl.object` — needs an adapter written by the developer rather than working unchanged.

The dispatch between the two kinds of child is resolved once, when the composite is constructed, so the hot path pays no per-`.validate()` `instanceof` check: a `pvl` Schema keeps being validated through `_validate` with its full path handed down, and only a non-class child pays for re-prefixing.
