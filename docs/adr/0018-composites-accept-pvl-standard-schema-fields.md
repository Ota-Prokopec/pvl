# Composites accept any pvl-produced Standard Schema as a field, re-prefixing the child's Issue paths

`ObjectSchema` and `ArraySchema` accept as a field or element any Standard Schema **that `@pvl/schema` itself produces** — an interpreted `Schema`, or a [Compiled Schema](../../CONTEXT.md) from `pvl.compile(...)` — not only an instance of this package's own `Schema` class. When a field is not one of those classes, the composite calls the child's `~standard.validate` and, for every `Issue` that comes back, prepends its own key (or array index) to the child's `path` before collecting it. Whether a child is a `Schema` instance is resolved once, at construction, so the per-value hot path pays for no dispatch.

This exists because a nested Compiled Schema is such a field. A Compiled Schema is a Standard Schema object and nothing more — it has no `_validate` and no place in `@pvl/schema`'s class hierarchy — so without this an interpreted parent could not hold a compiled child, and partial adoption of the compiler would not compose at all. Path re-prefixing is what makes that child satisfy [ADR-0012](./0012-composite-schemas-collect-every-issue.md)'s contract: the parent reports every failing field, each attributed to its own location, and a failure two levels inside a compiled child still names its full path from the outermost Schema, so a consumer's error rendering keeps pointing at the right field after the import swap.

Schemas from other libraries (Zod, Valibot, …) are **not** accepted, even though they implement the same protocol. An earlier draft of this decision accepted any Standard Schema; it was narrowed before anything was built on it. Two properties of a pvl-produced child are what a composite relies on, and a foreign schema guarantees neither. Its `validate` may return a `Promise`, which `@pvl/schema`'s synchronous-only `validate()` cannot honour. And its `Issue`s need not carry an `Issue.code`, so a parent's `Result` would stop being the coded `Issue` list [ADR-0011](./0011-result-failure-branch-carries-pvl-issue.md) promises consumers.

The restriction is enforced **at the type level only**, through `PvlStandardSchema`: a field's `~standard.vendor` must be the literal `'@pvl/schema'` and its `validate` must return `@pvl/schema`'s own synchronous `Result`. Every `Schema` therefore types its `vendor` as that literal rather than `string`. There is no runtime vendor check in the factories — it would cost a check on every construction to catch only a caller who has already cast past the type, and that caller is on their own. Nor is a field's result checked at validation time: a foreign `validate` cast past the type that returns a `Promise` hands that `Promise` back as the field's accepted value rather than raising an `Issue` or throwing.
