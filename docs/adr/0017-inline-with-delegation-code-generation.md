# Generated code inlines within a node and delegates at composite boundaries

The code `@pvl/schema-compiler` emits is straight-line JavaScript — literal `if` and `for` statements, no interpreter loop, no `new Function`, no instruction table walked at runtime. Within a single node, checks are inlined: a `pvl.object` with three string fields emits the three `typeof` tests directly in its own body. At a **composite boundary**, the parent does not re-inline the child's body; it calls that child's own emitted validator instead.

The boundary rule is what keeps output size sane. Inlining everything makes emitted code multiply with nesting depth, so a Schema used in several places, or one nested a few levels deep, produces output that grows far faster than the Schema it came from. Delegating at each composite keeps the emitted code linear in Schema size, and costs one function call per composite — which is exactly what the interpreted path already paid for that node, minus the tree walk, the key rediscovery and the per-field dispatch that the inlined primitive checks replace. Inlining primitives inside a node is free by comparison and is where the win actually comes from.

Issues are emitted as plain object literals matching `Issue` ([ADR-0011](./0011-result-failure-branch-carries-pvl-issue.md)), importing nothing from `@pvl/schema`. An individual Compiled Schema's instruction sequence is dependency-free in that sense; the [Destination File](../../CONTEXT.md) as a whole is not, because it also mirrors ordinary interpreted Schemas and therefore keeps `@pvl/schema` as a runtime dependency. The consequence of emitting Issues as literals is that nothing in the type system keeps the generated Issue — its message, its code, above all its `path` — in step with what the interpreted path would have produced. That is why the compiler's suite must diff compiled `validate()` against interpreted `validate()` under generated inputs, and why that differential test is load-bearing rather than a nicety: it is the only thing standing between a wrong Issue path in a nested array and production.

`.refine()` and `.transform()` bodies are never compiled. They are arbitrary user code; the emitted validator imports the original function by reference and calls it, so compiling can never silently drop the custom logic a developer attached.

The accepted cost is readability versus density: emitted code is meant to be read by a developer debugging a validation failure, so it stays as literal `if` statements with the source Schema's own key names rather than being minified or table-driven. Bundlers can shrink it afterwards; the compiler's own output optimises for being diffable and legible.
