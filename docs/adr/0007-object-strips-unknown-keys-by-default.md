# `object()` strips unknown keys by default

`pvl.object(shape)` silently strips keys not present in `shape` from the validated output unless the consumer opts into `.strict()` (report unexpected keys as `Issue`s) or `.passthrough()` (preserve them, untyped). Default-strip was chosen over default-strict so that validating a payload with stray/extra fields — the common case for data crossing a trust boundary (HTTP bodies, third-party API responses) — doesn't require every call site to explicitly opt out of failing on fields it doesn't care about; a consumer that actually wants to catch unexpected keys opts in explicitly via `.strict()` instead. The trade-off: a typo'd key in input data is silently dropped rather than flagged, unless the schema author opts into `.strict()` for that schema.

Stripping is itself a post-modifier ([ADR-0010](./0010-modifiers-run-in-chain-order-around-the-type-check.md)) that every object schema starts with, first in its chain. `_checkType` keeps every key, so the undeclared ones are still on the value it hands on; the strip modifier drops them. `.strict()` removes it and appends a post-modifier reporting the undeclared keys; `.passthrough()` only removes it. Each removes the other's too, so the last of the two chained wins. The unknown-key mode therefore applies to the whole chain rather than at the point it is chained: a `.refine()` on a `.passthrough()` schema sees the undeclared keys whether it was chained before or after it. Keeping the mode positional was the alternative, and it was rejected: a post-modifier chained after the strip would have to recover keys the strip already dropped, which needs the raw input stored somewhere outside the pipeline — module-level or on the schema instance, neither of which a Modifier shared across clones can use safely. There is no `.strip()` method: a later `.strip()` would only ever undo the other two, which chaining the one you want last already does.
