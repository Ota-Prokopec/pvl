# `object()` strips unknown keys by default

`pvl.object(shape)` silently strips keys not present in `shape` from the validated output unless the consumer opts into `.strict()` (report unexpected keys as `Issue`s) or `.passthrough()` (preserve them, untyped). Default-strip was chosen over default-strict so that validating a payload with stray/extra fields — the common case for data crossing a trust boundary (HTTP bodies, third-party API responses) — doesn't require every call site to explicitly opt out of failing on fields it doesn't care about; a consumer that actually wants to catch unexpected keys opts in explicitly via `.strict()` instead. The trade-off: a typo'd key in input data is silently dropped rather than flagged, unless the schema author opts into `.strict()` for that schema.

Stripping is `_checkType` never copying the undeclared keys onto the output it builds, as a compiled object's build never copies them, so the default costs no post-modifier and no second copy of the object. `.strict()` and `.passthrough()` remove the strip by setting the schema's `_keepsUnknownKeys`, after which `_checkType` copies the undeclared keys too ([ADR-0010](./0010-modifiers-run-in-chain-order-around-the-type-check.md) runs the post-modifiers on that output). `.strict()` also appends a post-modifier reporting them, and each removes `.strict()`'s post-modifier, so the last of the two chained wins. A compiled object follows the same rule (`ObjectSchema.unknownKeysMode`), and skips the copy only for a `.strict()` with no other post-modifier reading the output, which nothing can observe: with an undeclared key `.strict()` fails, so the output is never accepted, and without one there is nothing to copy. The unknown-key mode therefore applies to the whole chain rather than at the point it is chained: a `.refine()` on a `.passthrough()` schema sees the undeclared keys whether it was chained before or after it. Keeping the mode positional was the alternative, and it was rejected: a post-modifier chained after the strip would have to recover keys the strip already dropped, which needs the raw input stored somewhere outside the pipeline — module-level or on the schema instance, neither of which a Modifier shared across clones can use safely. There is no `.strip()` method: a later `.strip()` would only ever undo the other two, which chaining the one you want last already does.
