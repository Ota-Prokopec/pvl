# `Result`'s failure branch carries `@pvl/schema`'s own `Issue`

`Issue` extends `StandardSchemaV1.Issue` with a `code` field whose stated purpose is programmatic matching — a consumer distinguishing "wrong type" from "too small" from "failed a custom refinement" without string-matching the human-readable `message`. But `Result<Output>` was a plain alias of `StandardSchemaV1.Result<Output>`, whose failure branch types `issues` as the spec's `Issue`, so `code` was erased at the package boundary: it was present at runtime on every issue the library produced and unreachable from TypeScript. The field existed for a purpose its own public type made impossible.

`Result`'s failure branch is therefore `FailureResult = StandardSchemaV1.FailureResult & { readonly issues: ReadonlyArray<Issue> }`. The intersection is the point: `FailureResult` is _derived from_ the spec's type rather than re-declared alongside it, so it cannot drift from the spec as that spec evolves, which is what `packages/schema/AGENTS.md` and `docs/specification/standard-schema.md` forbid when they require one representation rather than "two parallel representations kept in sync by hand". Narrowing a property to a subtype keeps the whole type assignable wherever `StandardSchemaV1.Result` is expected, so `"~standard".validate` stays conformant and no Standard-Schema consumer sees a difference — they read the spec's fields and simply don't see `code`.

The rejected alternative was leaving `Result` aliased and having callers narrow with a type guard or assertion of their own. That pushes a cast into every consumer to recover a field the library always populates, which is worse ergonomics for the same runtime behavior, and it leaves the library's own tests unable to assert on `code` without the same cast.
