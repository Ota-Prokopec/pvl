# Code generation

What the code `@pvl/schema-compiler` emits looks like. Read this before you write or change an emit template.

## Everything inlined into one `_checkType`

Straight-line JavaScript: literal `if`/`for` statements, no interpreter loop and no `new Function`. Every check of the whole Schema is inlined into one `_checkType`, nested Schemas included. The parent never calls a child's `_checkType`, for speed. Output therefore grows with the size of the whole tree ([ADR-0023](../../adr/0023-compiled-schemas-inline-nested-schemas-and-mirror-schema-methods.md), superseding [ADR-0017](../../adr/0017-inline-with-delegation-code-generation.md)'s delegation).

A nested object or array is inlined where its parent reads it. Once its type check passes, its checks run in a block of their own, then the output they build replaces the value the parent read (`field0 = output1`), so a nested value is declared with `let`. Its locals are numbered across the whole class (`input1`, `path1`, `field3`, `index2`), and it keeps its own Issue path in one local (`const path1 = [...path, "lines"]`) that its fields' and element's paths extend (`[...path1, index1]`). Without that local, every Issue path would spell out every key above it, and output would grow faster than the Schema with each level of depth. What only runs once every field or element has passed (`.strict()`, an array's Constraints) is guarded by the count of Issues before the node (`if (issues.length === issueCount1)`), because every node pushes onto the one `issues` array.

## Emitters mirror `@pvl/schema`'s methods

The templates live in `src/emitters/`, one class per schema type (`StringSchemaEmitter`, `ObjectSchemaEmitter`, …), with only static methods named like the schema method they compile, plus `_emitBaseCheck({ schema, target, scope })` for the type check, which reads `schema` only when the check needs the factory's argument (`pvl.literal('a')`). Every method of an emitter takes one object, never positional parameters, so a hook or template destructures only what it reads. A template takes `{ target, args }`: `target` is an `EmittingCheckMethodInput` (the checked value and its full Issue path, as expressions) and `args` the mirrored method's own arguments. It returns an `EmittingCheckMethodOutput`: a check (its failing condition and Issue) or source text written in a `js` tagged template. Its type is `EmitterMethodOf<…>` of the `@pvl/schema` method it mirrors (`EmitterMethodOf<StringSchema['min']>`), so its `args` are that method's own parameters and a change to them fails the compiler's type check. The compiler dispatches a chained method to the emitter method of the same name, so adding a method to an emitter is what makes that method compile.

The emitters extend each other the way the schemas do. The base `Emitter` stands in for `Schema` and does the emitting, following the pipeline of [ADR-0010](../../adr/0010-modifiers-run-in-chain-order-around-the-type-check.md): a Schema's pre-modifiers' conditions guard its base check (`_emitBaseCheck`, the type check), and what runs once that has passed (`_emitTypedChecks`) comes after it. For a primitive, that is its post-modifiers' checks. A composite's emitter overrides it to inline its children's checks first, as `_checkType` runs every child, then its post-modifiers', which run only once every child has passed, then to hand on the output it builds. The calls come from the compiler `Schema`'s two arrays, `preModifierCalls` and `postModifierCalls`: reading a Schema splits its chained methods into them, each in chain order, as `@pvl/schema` adds a Modifier to its pre- or post-modifiers (`PRE_MODIFIER_NAMES`). `emitSchemaChecks` writes one Schema's checks where its parent reads the value, and `emitCompiledSchema` writes them at the root, as the Compiled Schema's class. A composite's emitter writes its checks once for both: its `CompositeFrame` names its locals and holds all that differs, as the root returns its first Issues and then its output, while a nested composite guards its post-modifiers by the Issue count and puts its output back on the value.

`ChainableSchemaEmitter extends Emitter` adds `.optional()`/`.nullable()` and widens the types for them, and every schema's emitter extends it. A subclass overrides only the `_`-prefixed hooks: `_emitBaseCheck`, `_spellFactoryTypes` when its factory takes an argument (`pvl.literal('a')`) or nests Schemas, and, for a composite, `_emitTypedChecks` and `_spellValueDeclaration`. Each hook takes the compiler `Schema` subclass its Emitter compiles (`ObjectSchemaEmitter._emitTypedChecks({ schema, target, scope, isRoot }: EmitTypedChecksArgs<ObjectSchema>)`), and a nested Schema's Emitter is the one it names (`schema.emitter`). `EmitScope` carries what one class's emitting shares: the numbering of its locals. Neither a name starting with `_` nor a method the base `Emitter` declares is ever dispatched as a chained method. The compiler's abstract `Schema` (`src/schemas/schema.ts`) reads each factory into its own subclass (`src/schemas/`), which names its Emitter, and reports what can't be compiled yet ([ADR-0026](../../adr/0026-the-compiler-reads-each-factory-into-its-own-schema-subclass.md)).

An emitted Issue's message comes from `@pvl/schema`'s `<SCHEMA>_SCHEMA_ISSUE_MESSAGE`, called at compile time and written as a literal. A message that names a runtime value (`.strict()`'s unknown key) is built at runtime around that message's literal text.

## Each Compiled Schema is a `Schema` subclass

Each `pvl.compile(...)` call becomes, in its mirrored module, a class `PvlCompiledSchema<n>` (counted in source order) placed after the module's imports, and the call becomes `new PvlCompiledSchema<n>()`. The class extends `@pvl/schema`'s `Schema`, imported under an alias so it can't clash with the module's own names, and its `_checkType` is the generated code. Its `Input` and `Output` type arguments are spelled out from the Schema, so it infers the types `pvl.compile()` does. [`schema/compile.md`](../schema/compile.md) holds the contract that class fills: empty modifier arrays, every `Issue` reported at the `path` it is handed, and a typed surface identical to what `pvl.compile()` returns before compilation, so the import swap is a drop-in at the type level too. It inherits `"~standard"` and reports `vendor: "@pvl/schema"` ([`standard-schema.md`](../standard-schema.md#conformance-rules)).

## Issues are literals, so the differential test is load-bearing

Each `Issue` ([ADR-0011](../../adr/0011-result-failure-branch-carries-pvl-issue.md)) is a plain object literal, importing nothing, with its code, message and path written out. Nothing but the differential test against the interpreted path keeps them right, which is why that test is load-bearing, not optional.
