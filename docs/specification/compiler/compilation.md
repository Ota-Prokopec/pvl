# Compilation

How `@pcvl/compiler` finds a schema marked with `pvl.compile(...)` and what it compiles. Read this before you work on discovery, or on which schema a marker compiles. [`schema/compile.md`](../schema/compile.md) defines `pvl.compile()` itself and the runtime shape a Compiled Schema must fill.

## Discovery: static AST analysis, not dynamic import

The compiler never runs or imports the user's schema code. It statically parses the TS/JS source of the files matched by `include` in the user's `pvlconfig.json`, using ts-morph, looking for `pvl.compile(...)` call expressions. See [ADR-0002](../../adr/0002-static-ast-compilation-via-ts-morph.md) for why (never executing user code; the trade-off is that only statically-resolvable schema expressions are compilable, and marking one that isn't is an error rather than a silent fallback).

## What reads statically

A call is recognised when `pvl` is imported from `@pcvl/schema` under any name and the name it is called on is bound to that import, so a parameter or a local that shadows it marks nothing. Its argument may be a `pvl.*` call chain written in place, or a top-level `const` holding one, followed through any number of `const`s, in the same file or into the file an import names ([ADR-0043](../../adr/0043-the-compiler-follows-a-const-into-another-file-and-a-runtime-argument-there-is-an-error.md)): a named, aliased or default import, through any `export { … } from` or `export *` barrel and any tsconfig `paths` alias, into a file `include` matches or not, symlinked or not. That file's own Local Names of `pvl` read it. A default-exported expression and a namespace import's property (`schemas.user`) hold no `const`, so they aren't followed, and the error says how to write them so they are. A name is bound in its scope, as JavaScript binds it, so a parameter or a local that shadows a top-level `const` is not that `const`, and isn't followed (`const kind = 'user'; (kind: 'admin') => pvl.compile(pvl.literal(kind))` reads no `'user'`). This binds names only and checks no type ([ADR-0024](../../adr/0024-the-compiler-checks-syntax-not-types.md)). A method's arguments read statically only when they are literals written in place (`3`, `-1`, `10n`, `'a'`, `{ message: 'too short' }`), under any number of `!`, `-` and `+` (`!0`, `!!!flag`, `+'2'`, `-+1`), and are then written into the checks as literals. A method's argument never follows a `const`: one naming a `const`, anywhere in it, is a Runtime Argument (below), so a later change to an object the `const` holds and its declaration order count as they do in the interpreted path ([ADR-0030](../../adr/0030-a-method-argument-the-compiler-cant-read-is-a-runtime-argument-evaluated-once-where-it-is-written.md)). `++`, `--` and other assignments are never read, as they need the variable's runtime state ([ADR-0025](../../adr/0025-static-reading-never-evaluates-an-assignment.md)). A plain `__proto__: …` in an object literal sets the prototype rather than adding a key, so it is no field, while `['__proto__']: …` is one. `pvl.compile()` may wrap any Schema, primitive or composite ([ADR-0016](../../adr/0016-transform-and-compile-end-the-modifier-chain.md)), and what it wraps compiles at the root just as it would nested. Anything else gets an error, and nothing is written. A call that can't be read, or whose result is modified, gets one; a call that reads but isn't a Compilable Schema gets one per problem:

- `COMPILE_ARGUMENT_UNRESOLVABLE`: the argument, or a factory's argument, is built by a function call, spread, held in a `let`, a parameter or a local that shadows a top-level `const`, an assignment such as `++count`, a default-exported expression or a namespace import's property; or a method argument is spread.
- `RUNTIME_ARGUMENT_IN_IMPORTED_SCHEMA`: a Schema followed into another file passes a Runtime Argument written there, such as a function given to `.refine()`. It is evaluated where it is written (below), so it can't be inlined into the file being compiled ([ADR-0043](../../adr/0043-the-compiler-follows-a-const-into-another-file-and-a-runtime-argument-there-is-an-error.md)).
- `COMPILE_ARGUMENT_CYCLE`: the argument, or a factory's argument, follows a `const` that refers back to itself (`const user = pvl.object({ friend: user })`), so reading it would never end. TypeScript reports such a `const` as used before its declaration, but the compiler doesn't type-check ([ADR-0024](../../adr/0024-the-compiler-checks-syntax-not-types.md)).
- `COMPILE_RESULT_MODIFIED`: something other than `.validate()`, `.standalone()`, `shape` or `element` is read off the result (`pvl.compile(x).optional()`).
- `UNSUPPORTED_SCHEMA`: the Schema uses what isn't compiled yet. Today that is a union, at any depth, the wrapped Schema included: primitives, literals, enums and objects and arrays of them compile, with their Constraints, `.strict()`/`.passthrough()` and every Shared Modifier. A method `@pcvl/schema` doesn't have gets it too, called on `pvl` (`pvl.foo()`) or chained onto a Schema (`pvl.string().foo()`): such a call can't be read, so it ends the reading and is the call's one error, after any receiver that can't be read ([ADR-0038](../../adr/0038-pvl-ast-narrows-method-names-and-an-unknown-one-ends-the-reading.md)). A method another Schema has (`pvl.string().strict()`) reads, and is one problem among the others.

## `.standalone()` is a marker, not a Modifier

`.standalone()` changes no check, so reading a Schema takes it off the chain wherever it is written, and records only that the Schema is a Standalone Key: `pvl.compile(x.standalone())` and `pvl.compile(x).standalone()` read the same. It never produces a diagnostic, compiled or not, as a marked Schema may be defined in one file and used as a field in another. What it changes is what a Compiled Schema exposes: a compiled object's `shape` holds the Compiled Schema of each Standalone Key, and a compiled array's `element` is a Compiled Schema when its element is marked ([code-generation.md](./code-generation.md#a-compiled-schema-exposes-its-standalone-keys), [ADR-0036](../../adr/0036-standalone-keys-are-reinstated-and-shape-and-element-survive-every-call-but-transform.md)).

## Runtime Arguments

A method's argument that doesn't read statically is a Runtime Argument, which the Compiled Schema evaluates: a `const`, a parameter, a `let`, an import, a call, a property read or an operator, `++count` included ([ADR-0030](../../adr/0030-a-method-argument-the-compiler-cant-read-is-a-runtime-argument-evaluated-once-where-it-is-written.md)). Only a spread one has no fixed position to be passed at, so `.max(...limits)` and `{ ...options }` written in place are `COMPILE_ARGUMENT_UNRESOLVABLE`. A factory's argument never is one: it decides the Schema's types or the structure that is inlined, so it must read statically.

Each Runtime Argument is evaluated once, where it is written, as the interpreted path evaluates it, so it must be written in the file being compiled: one written in the file an Imported Schema is followed into is `RUNTIME_ARGUMENT_IN_IMPORTED_SCHEMA` ([ADR-0043](../../adr/0043-the-compiler-follows-a-const-into-another-file-and-a-runtime-argument-there-is-an-error.md)), while one chained onto an Imported Schema in the file being compiled is passed as any other. Written inside the `pvl.compile(...)` call, it is passed as written to the Compiled Schema's constructor, which replaces the call ([code-generation.md](./code-generation.md#runtime-arguments-go-through-the-constructor)). Written in a top-level `const` the call follows, it is hoisted into a `const pvlArg<n>` right before that `const`'s declarator, which then reads it, and the call passes that name ([destination-directory.md](./destination-directory.md)). A plain name is hoisted too (`const pvlArg0 = MAX;`), as at the call it could name a parameter that shadows it. Either way it runs once per evaluation of the code it is written in: `pvl.compile(pvl.string().max(getMax()))` at the top level calls `getMax()` once, and `() => pvl.compile(pvl.string().max(getMax()))` once per call.

## Compilation unit: exactly what `pvl.compile()` wraps

`pvl.compile()` is per-call-site: each call produces its own Compiled Schema for exactly the schema it wraps, whether that's a whole top-level schema (`pvl.compile(pvl.object({...}))`) or one nested field (`pvl.object({ key: pvl.compile(pvl.object({...})) })`). Compiling a nested field does **not** reach up and compile its containing schema — the parent stays an ordinary interpreted `Schema` regardless; if a fully-compiled top-level schema is wanted, wrap the top-level schema itself.

## Modifiers are baked in

Every Modifier is applied **before** compiling and baked into the emitted code, running in the same order and with the same short-circuit and collection rules as the interpreted path ([`schema/pipeline.md`](../schema/pipeline.md), [ADR-0010](../../adr/0010-modifiers-run-in-chain-order-around-the-type-check.md)), at the root as on a nested field or element ([ADR-0035](../../adr/0035-modifiers-compile-to-calls-to-the-users-own-functions-typed-at-their-place-in-the-chain.md)):

- `.optional()` and `.nullable()` are leading checks that accept the value as it is, and `.coerce()` is a conversion inlined where it is chained among them, as `@pcvl/schema`'s `coercions.ts` converts. Only the four primitives and `literal` have one, so `.coerce()` on an object, an array or an enum is a method its Emitter doesn't hold, and reported `UNSUPPORTED_SCHEMA`.
- Only the _structural_ checks (type guards, required-field checks, array iteration, Constraints) become `Instruction`s. `.refine()` and `.transform()` bodies are arbitrary user code, never inlined or compiled: each function is a Runtime Argument (below), evaluated once where it is written, which the Compiled Schema calls. The Destination Directory mirrors the module it is written in, so it is reached as it was in source, imported or not.
- A `.refine()` reports a `CUSTOM` Issue, in chain order among the Constraints and `.strict()`, reading what the interpreted one reads: a composite's output, not its input. A `.transform()` replaces the value once nothing in its Schema failed, after a short-circuit too, and its function's return type is inferred as the interpreted `.transform()` infers it.
